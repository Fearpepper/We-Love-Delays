# Real-phone transit ride checks

Automated browser checks do not verify an iPhone GPS receiver, bus arrival accuracy, or background reminders. These checks need a rider physically on a real bus. None are marked passed by software.

Use Safari on an iPhone, then repeat with the installed Home Screen app. Record the phone/iOS version, test date, bus route/direction, public stop codes, and expected versus observed behavior. Do not publish a GPS trace or personal home address.

1. Select the actual origin and destination. Compare nearby departures with the stop sign/official AC Transit source. Check direction and the live/schedule label. A schedule must never be described as live.
2. Start the trip outdoors. Allow location, verify the blue dot and accuracy circle, then move. The map should follow without changing zoom. Dragging pauses following; Recenter resumes it. A denied permission must leave written directions usable.
3. Mark boarding manually. Check that the rider's bus and direction match the trip. Predictions can be missing or ambiguous; unverified delay must not earn fictional points.
4. Lock the phone briefly and reopen it. Position must update before it is trusted. If the browser pauses GPS, the app must explain stale reception. Do not depend on a lock-screen get-off notification.
5. With the app open and accurate GPS, approach the exit stop. Verify the reminder against the actual stop. It must not mark alighting automatically. Confirm alighting yourself and check transfer walking directions.
6. Before boarding, use “I missed it” and verify the next catchable scheduled option. The destination and current trip must stay intact until a replacement is selected. During a ride, choose the actual current origin rather than assuming the next stop is your location.
7. Briefly disconnect data, reopen, and reconnect. Written/saved bus steps should remain usable; current arrivals should become unavailable offline and refresh when requested after reconnecting.
8. Finish once. Verify the completion message and wallet explanation, then reload. No duplicate reward or invented delay should appear. Rewards remain fictional.

Report a failure through Something wrong in Guide. Saving keeps the report on the device; the rider can copy/download it or review and submit a public GitHub issue. Stop codes and route IDs are attached, not GPS coordinates. Remove personal details before publishing.

For each check record: PASS / FAIL / NOT TESTED, observed behavior, and a screenshot if helpful. Repeat one direct ride and one transfer trip in both good and poor reception. Do not call field testing complete until actual ride results have been recorded.
